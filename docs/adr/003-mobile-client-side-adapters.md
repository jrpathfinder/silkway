# ADR-003: Клиентские адаптеры для мобильного приложения

## Решение

Flutter-приложение (`apps/customer`) применяет тот же принцип портов и адаптеров, что и backend (ADR-002), но на стороне клиента. Каждая интеграция с backend (`locations`, `catalog`, `auth`, `orders`, `payment`, `delivery`, `loyalty`, `notifications`, `courier`), а также абстракция карт (`MapProvider`, будущий Yandex MapKit), оформлена как абстрактный класс-порт с двумя реализациями: `*RepositoryMock` (фикстуры) и `*RepositoryHttp` (реальный запрос через `dio`). Переключение между ними выполняется одним Riverpod-провайдером, читающим флаг `--dart-define=USE_MOCKS`, — это зеркалирует серверный `DatabaseService.enabled` + fallback-фикстуры (`CatalogService.fromFallback`).

Приложение — одно, с двумя «флейворами» (customer/courier), запускаемыми через отдельные entry point'ы (`main_customer.dart`, `main_courier.dart`), с общим `core/` пакетом (модели, сеть, storage, дизайн-система). Отдельного Flutter-проекта для курьера нет.

Состояние — Riverpod. Навигация — `go_router` с раздельными таблицами маршрутов на флейвор; авторизация не блокирует просмотр каталога/корзины, только `/checkout` и `/orders/**`. Оплата — hosted checkout в in-app `webview_flutter` (не внешний браузер), чтобы не терять контекст приложения и уметь автоматически определять завершение оплаты.

## Причины

Пользователь явно запросил разработку архитектуры мобильного приложения в первую очередь, с бэкендом — параллельно или позже. Это требует, чтобы любой экран мог быть построен и продемонстрирован против моков ещё до готовности соответствующего backend-эндпоинта, без переписывания кода при переходе на реальный API — ровно то, что решают порты и адаптеры на backend.

## Известные пробелы в контракте (обнаружены при проектировании)

- `AuthService.verifyOtp` не возвращает id клиента — только `{accessToken, refreshToken, user:{phone}}`. Клиент временно использует номер телефона как `customerId` (совпадает с `customer.phone_e164` в `schema.sql`).
- Нет HTTP-маршрута для списка заказов клиента: `OrdersService.listForCustomer` существует, но не подключён ни к одному route в `orders.controller.ts`. История заказов в приложении работает только на моках.
- Нет backend-модулей `delivery` (есть только пустой порт `DeliveryProvider`), `loyalty`, `notifications` — соответствующие клиентские репозитории мок-only, `*RepositoryHttp` — заглушки, бросающие `UnimplementedError`.
- Токены dev-стаба (`auth.service.ts`) статичные, без срока действия — клиент пока не реализует refresh-flow, только `// TODO` в `ApiClient`'s interceptor.
