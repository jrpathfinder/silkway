# Статус интеграций

EN: [`../en/integrations.md`](../en/integrations.md). Обновляйте обе версии вместе.

Все четыре порта — в `apps/api/src/modules/integrations/ports/*.port.ts`. Конкретные провайдеры привязываются в `integrations.module.ts`, переключаются переменной окружения, по умолчанию всегда мок.

## SMS (доставка OTP) — реально, код готов

- **Порт**: `SmsProvider` (`sms.port.ts`)
- **Провайдеры**: `MockSmsProvider` (логирует код вместо отправки) / `SmsRuProvider` (настоящая интеграция [sms.ru](https://sms.ru))
- **Переключатель**: `SMS_PROVIDER=mock|sms.ru`, в реальном режиме нужен `SMS_RU_API_ID`
- **Статус**: код рабочий, проверен против настоящего API sms.ru. Сейчас заблокирован **снаружи**, не в коде — sms.ru отклоняет доставку, пока в аккаунте не зарегистрировано буквенное имя отправителя (в личном кабинете sms.ru). После одобрения никаких правок кода не нужно — просто вернуть `SMS_PROVIDER=sms.ru`.
- **Удобство для разработки**: пока активен мок-провайдер, ответ `AuthService.requestOtp` содержит поле `devCode` с настоящим кодом — Flutter-приложение показывает его прямо на экране ввода кода, читать логи сервера не нужно. При реальном провайдере этого поля никогда нет.
- **Ограничение частоты**: `OtpStore` хранится в Redis, если задан `REDIS_URL`, иначе — в `Map` в памяти процесса (та же опциональная схема, что у `DatabaseService`) — см. [CLAUDE.md](../../../CLAUDE.md).

## Фото блюд — своё хранение, код готов

- **Без порта/провайдера** — в отличие от остальных четырёх, это не подключаемая сторонняя интеграция, а обычное хранение на диске за эндпоинтом загрузки.
- **Загрузка**: `AdminUploadsController` (`admin-uploads.controller.ts`), `POST /v1/admin/uploads`, защищён admin-авторизацией, только JPEG/PNG/WebP, максимум 5 МБ. Пишет в `UPLOADS_DIR` (по умолчанию `apps/api/uploads/`) и возвращает абсолютный URL (`PUBLIC_BASE_URL` + путь) для сохранения в `CatalogItem.imageUrl`.
- **Отдача**: статический маунт в `main.ts`, а не Nest-роут — обычные файлы, как отдавал бы CDN.
- **Не обязательно**: `imageUrl` — по-прежнему просто строковая колонка, вставить внешний URL напрямую (засеянное меню сейчас именно так использует CDN Яндекс.Еды) работает точно так же, как раньше. В форме блюда в админке есть оба варианта: поле URL и загрузка файла, которая сама заполняет это поле.

## Оплата — реально, код готов

- **Порт**: `PaymentProvider` (`payment.port.ts`)
- **Провайдеры**: `MockPaymentProvider` / `YookassaPaymentProvider` (настоящий ЮKassa REST API v3)
- **Переключатель**: `PAYMENT_PROVIDER=mock|yookassa`, в реальном режиме нужны `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`
- **Статус**: проверено целиком против настоящего тестового API ЮKassa — создана настоящая платёжная сессия, оплата завершена тестовой картой ЮKassa прямо через WebView приложения, подтверждено, что вебхук сработал и статус заказа обновился корректно.
- **Вебхук**: живёт в `apps/api/src/modules/orders/payment-webhook.controller.ts`, а не в `integrations/` — ему нужен `OrdersService` для обновления статуса заказа, а `OrdersModule` уже импортирует `IntegrationsModule` (не наоборот — иначе был бы цикл импортов). ЮKassa не подписывает тело вебхука, поэтому обработчик никогда не доверяет ему напрямую — при любом уведомлении он заново запрашивает платёж у API ЮKassa своими же учётными данными и действует только по этому авторитетному ответу.
- **Dev-поток в мок-режиме**: `MockPaymentProvider.createPayment` отправляет WebView на `GET /v1/mock-checkout` — настоящую страницу с кнопкой «Оплатить», которая зовёт `POST /v1/orders/:id/mark-paid-demo` — ручной curl для завершения тестовой покупки локально не нужен.
- **Как получить тестовые данные ЮKassa**: регистрация настоящего юрлица для тестовых ключей не нужна. В личном кабинете ЮKassa **тестовый магазин** создаётся автоматически при онбординге, и его собственные shopId и секретный ключ (в разделе Настройки → Ключи API / Интеграция → Ключи API именно ЭТОГО тестового магазина, а не шлюза выплат — это другой продукт с другим ключом) работают сразу, независимо от того, завершена ли анкета для настоящего бизнеса.
- **Не сделано**: возврат средств реализован в провайдере, но не проверен целиком; в админ-панели пока нет UI для его запуска.

## Доставка — не начато

- **Порт**: `DeliveryProvider` (`delivery.port.ts`) — `quote` / `create` / `cancel`
- **Провайдеры**: ни одного. Даже мока нет, и порт вообще не привязан в `integrations.module.ts`.
- **Переменные окружения есть, но не используются**: `DELIVERY_PROVIDER`, `YANDEX_DELIVERY_ENABLED`

## Маркетплейс (живая синхронизация с Яндекс.Едой) — не начато

- **Порт**: `MarketplaceMenuAdapter` (`marketplace.port.ts`) — `publishMenu` / `pullOrders` / `acknowledgeOrder`
- **Провайдеры**: ни одного, как и с доставкой.
- **Не путать с импортёром меню**: `tools/import-yandex-menu.mjs` (скачивает сырой JSON меню из Яндекс.Еды, разово) и `tools/map-yandex-menu.mjs` (маппит его в формат импорта каталога админки) — реальные, рабочие, и ими же реально засеяно настоящее меню ресторана в каталог. Но это разовый скрипт миграции, а не живая двусторонняя синхронизация этого порта. Построить порт по-настоящему — отдельная, более крупная задача.
- **Переменная окружения есть, но не используется**: `YANDEX_EDA_ENABLED`
